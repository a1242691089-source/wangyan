# V0.3b：按书筛选、关系计数与 i18n 棘轮

日期：2026-11-05　前置：V0.3a（7caea2e）

## 做了什么

| 能力 | 实现 |
|---|---|
| 按书筛选 | 知识页第二行 chips（「全部书籍」+ 有知识的书），与标签筛选 AND；纯函数 `filterKnowledgeCards(cards, tag, bookId = null)` |
| 书列表派生 | `deriveKnowledgeBooks(cards)`：distinctBy bookId，`Collator(Locale.SIMPLIFIED_CHINESE)` 排序，已删书（title=null）置末 |
| 关系计数 | `knowledge_relations` 聚合查询 → `KnowledgeCard.relationCount`，卡片底部 `AppIcons.Link` + 「N 条关系」 |
| 筛选空状态 | 全部知识非空但筛选无命中时给出提示 + 「清除筛选」（两轴一起清） |
| i18n 棘轮 | `StringsRatchetTest`：各 locale 相对 values 的缺失 key 数只降不升 |

## 关键决策

### 1. 计数口径：UNION ALL 计边数
```sql
SELECT nodeId, COUNT(*) AS count FROM (
  SELECT sourceNodeId AS nodeId FROM knowledge_relations
  UNION ALL
  SELECT targetNodeId AS nodeId FROM knowledge_relations
) GROUP BY nodeId
```
A→B 与 B→A 各计 1，与详情页 `observeRelationsForNode`（任一端命中）口径一致。自环被 `addRelation` 的 require 拦住，无需 SQL 排除。

取数走独立 Flow 再在仓库层三层 combine，而不是把 COUNT 塞进 `observeNodesWithEvidence` 的 `@Relation`：后者只能按 FK 取行，聚合要额外子查询且不容易被 Room 校验。

### 2. 筛选是 AND，默认参保持旧调用
`filterKnowledgeCards` 加 `bookId: String? = null` 而不是新函数：既有 2 参调用（旧 ViewModel、3 条既有单测）零改动，AND 语义集中在一处，后续加维度（标签多选、时间范围）也只在这里长。

### 3. 排序用 Collator 而非 String.compareTo
首版实现用 `compareBy({ it.title == null }, { it.title.orEmpty() })`，测试断言「论语」在「庄子」前失败——`String` 比较是码点序（庄 U+5E84 < 论 U+8BBA），中文书名排出来是乱序。改用 `Collator.getInstance(Locale.SIMPLIFIED_CHINESE)`（拼音序），`nullsLast` 让已删书落底。

### 4. i18n 棘轮为什么不是严格相等
实测漂移：en=17、ja=277、ko=277、zh-rCN=178、zh-rHK/MO/TW=269 缺失。严格相等会立刻红，一次补齐近千条翻译也不现实。棘轮取「缺失数 ≤ 基线」，新增功能漏翻会让数字上升而失败，逐月补翻译只会让它下降；基线写在测试文件里，下调必须在 PR diff 里露出来。

`resDir()` 三级 fallback（`src/main/res` → `user.dir/src/main/res` → 父目录 `app/src/main/res`）：Gradle 单测工作目录是模块目录，IDE 可能不同。目录按 locale 白名单显式打开，`values-night`/`values-v31` 天然不进扫描。

## 遗留
- 标签多选 / 与书筛选的联合计数（当前单选，点已选中的 chip 取消）
- 知识页按书分组视图（现在只有平铺 + 筛选）
- 关系计数只显示数量，卡片上不展示关系类型与对端（详情页承担）
- 基线数字需要随翻译补齐定期下调（否则棘轮只防新增、不防老账）
