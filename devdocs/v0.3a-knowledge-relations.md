# V0.3a 知识关系与详情页 · 设计笔记

> 对应 MIGRATION_21_22、`knowledge_relations`、`KnowledgeDetailScreen`、Reader 证据定位跳转。

## 1. 关系表的方向语义

`knowledge_relations` 是**有向边**（source → target），A→B 与 B→A 是两条独立记录：

- 唯一约束 `UNIQUE(sourceNodeId, targetNodeId, relationType)`：同一对节点、同一类型只存一条；
- 同一对节点允许**不同类型**并存（「支持」与「延伸」可以同时成立）；
- 自环（A→A）在 Repository 层 `require()` 拦截，不写 CHECK 约束 —— 保持 Room schema 与手写迁移逐字段一致，避免以后 `validateMigration` 因额外 CHECK 失败；
- 两端节点 FK 均 CASCADE，与 `knowledge_evidence.nodeId` 一致：删节点必须连带删边，不留孤儿。`bookId` 依然不设外键（删书不毁知识）。

类型存 TEXT（`KnowledgeRelationType.stored`），对齐 `notes.type` 先例：新增类型只改枚举，不需要迁移。未知值回退 `RELATED_TO`，保证旧数据不消失。

## 2. 九类关系为什么全量落地

方案原文列了 9 类（mentions / explains / supports / contradicts / extends / belongs_to / applies_to / exemplifies / related_to）。虽然首版是手动建边、多数类型用得少，但**枚举与入库值是纯追加成本**，而事后补类型要写数据迁移；且详情页的关系 chips 本身就是 9 选 1 的列表，不做筛选、不做推荐，全量不增加交互复杂度。真正需要后置的是「关系的自动抽取与推荐」，不是类型集合。

## 3. 详情页只读的边界

V0.3a 的详情页 = 节点内容（标题/理解/标签）+ 证据链 + 双向关系 + 删除。

编辑理解/标签**不在本版**：编辑需要复用 `NoteInputSheet` 的输入态与保存语义（首行派生 title、标签归一化），牵动写入链路；而本版主线是关系图谱的地基。数据层已支持更新（`insertNode` 为 REPLACE），补 UI 时不改表。

卡片点击从「打开书」改为「进详情」：开书行为没有丢失，而是下沉到证据条目的「定位阅读」，且带精确位置，比原来只能落到书首更符合「证据回链」的产品意图。

## 4. 证据定位跳转：为什么改路由而不是新建页面

阅读器已有精确字符定位机制：`ReaderUiState.pendingReaderPosition: ReaderPositionLocator?`，分页引擎在 `ReaderScreen.kt:2032` 调 `readView.jumpToCharacter(...)`，连续滚动在 `3295` 行用 `initialCharacterOffset` 落位。因此证据跳转只需把目标写进 `pendingReaderPosition`，渲染层零改动。

`startPosition` 的语义已核实为**章节内字符偏移**：`HighlightAnchorResolver` 直接把它当章节文本下标使用，TXT 另经 `characterOffsetToByte` 换算字节偏移。

路由采用可选 query 参数 `reader/{bookId}?chapter={chapter}&position={position}`，默认 -1。`createRoute(bookId, chapter = -1, position = -1)` 带默认值，既有调用点（NavGraph 522/528/543/569/786 等）零改动；`NavGraph` 里所有 `currentRoute == Screen.Reader.route` 的比较仍用同一常量，过渡动画与返回逻辑不受影响。

`loadBook` 的接线点只有一处：算出 `evidenceJumpLocator` 后覆盖 `startChapter` / `pageFraction` / `pendingReaderPosition`，并把 `pendingPageFractionSemantics` 在有目标时固定为 `START`（否则冷启动无历史进度会被当成 `INCLUSIVE_PAGE_END`，落点偏一页）。

## 5. 原排版（BOOK_LAYOUT）降级为章首

EPUB 原排版走 WebView 渲染，字符偏移没有意义；精确定位需要拿 `startLocatorJson` 走搜索解析链路（`HighlightTextReference`），成本与风险都属另一个量级。本版对 `BOOK_LAYOUT` 只保留章首定位（`characterOffset = null`，走 `jumpToChapter`），精确定位后置 V0.3b。

## 6. 同步位与墓碑

新表带 `syncId`（unique）+ `updatedAt`，删除关系写 `SyncTombstoneEntity("knowledge", relation.syncId, ...)`，命名空间与节点删除一致。服务端同步协议后补时不改表。
